## 1. Executive decision

**v3.0.0 phase gate: PASS WITH RECORDED DEFERRED GATES.**

The repository is healthy enough to begin **v3.0.1 local NATS JetStream shadow mode**. The existing REST heartbeat, command polling, PostgreSQL persistence, dashboard, AI, supervisor, and three SimPy process nodes all pass the canonical regression and strict runtime checks.

The audit does **not** claim that the system is already distributed. The current accepted deployment is one Windows host running eight supervised processes. Five VirtualBox guests are registered, but none is running, the three production guests have NAT only, and the Host-Only adapter is not on the intended management subnet. Those facts block later cross-VM migration stages, not the local v3.0.1 transport experiment.

## 5. Persistence audit

### 5.1 Live PostgreSQL facts

- Server: PostgreSQL 16.14.
- Runtime database/user: `mini_ogas` / `mini_ogas`.
- Live public tables: 21.
- Live indexes: 36, including primary/unique indexes.
- `event_store`: 693 rows at audit time.
- `heartbeat_shadow`: 6,034 rows at audit time.
- `command_shadow`: 55 rows at audit time.
- `audit_logs`: 7,370 rows at audit time.

`event_store` already has the two idempotency boundaries required by the NATS worker:

1. primary key on `event_id`;
2. unique index on `(source_node, run_id, local_sequence)`.

The NATS worker must reuse these constraints and treat a duplicate insert as an idempotent acknowledgement, not as a fatal error.

### 5.2 Schema drift

`database/central-schema.sql` declares 20 tables and 3 explicit indexes. The live database has 21 tables and 36 total indexes, and its table set is not identical to the static file. The executable schema in `app/core/database.py` and prior runtime migrations currently define more of the accepted runtime shape than the static SQL file.

This is a real architecture debt item, but it does not block v3.0.1 because the required durable targets (`event_store`, `heartbeat_shadow`, `command_shadow`, and `audit_logs`) exist and were queried successfully. It becomes a hard gate before any fresh-host or cross-VM deployment: one authoritative migration path must recreate the same schema from an empty database.

## 6. Agent and security audit

### 6.1 Current protocol

The current canonical heartbeat path is:

```text
POST /agents/{node_code}/heartbeat
```

It accepts heartbeat v2 fields for status, metrics, production, alarms, synchronization, and runtime metadata. Commands are pulled through the REST pending-command endpoint. Offline records are replayed through `POST /node-records/sync` with batches of at most 100 records.

The old `POST /node-heartbeats` path remains a tested deprecated wrapper. v3.0.1 must preserve both paths and may only publish an additional NATS copy after the accepted REST transaction.

### 6.2 Current token reality

The supervisor startup script assigns the same runtime secret to `OGAS_API_TOKEN`, `API_ACCESS_TOKEN`, and `NODE_INGEST_TOKEN`. All three SimPy nodes therefore share one node credential. Middleware limits that credential to node-ingest routes, but it is not node-specific and cannot prevent one compromised node from impersonating another node.

The v3.0 contract freezes three distinct scopes and requires unique edge credentials. This separation is **not implemented in v3.0.0** and is not claimed as complete. It is a hard gate before the first edge VM is allowed to publish to a non-loopback NATS endpoint.

## 8. v3.0.1 readiness decision

### 8.1 Non-blocking gaps

The following are expected inputs to v3.0.1, not reasons to stop it:

- NATS Server and NATS CLI are absent.
- `nats-py` is absent.
- no Central `EventPublisher` or `NATSPublisher` exists.
- no JetStream stream or durable consumer exists.
- no NATS health field exists in Central health output.

### 8.2 Conditions for proceeding

v3.0.1 may proceed because:

- the canonical baseline and strict runtime gates pass;
- PostgreSQL is live and has durable idempotency constraints;
- the REST path is healthy and can remain authoritative;
- D drive has enough space for the server binary and JetStream data;
- local loopback operation avoids the unresolved VM, NTP, CA, and token-isolation gates;
- the working-tree changes are preserved and known, so no reset or destructive cleanup is required.

### 8.3 Hard v3.0.1 exit gates

v3.0.1 is not complete until all of these are evidenced:

1. NATS Server runs with JetStream data on D drive.
2. Publisher payloads validate against `contracts-v3.0.md` before publish.
3. REST remains the accepted path and NATS remains shadow-only.
4. NATS outage produces explicit `degraded`, never a Central crash or false success.
5. A durable worker consumes a message and writes one idempotent `nats_shadow_receipts` row to PostgreSQL without reapplying the REST business mutation.
6. Redelivery does not create a second durable fact.
7. New tests, the canonical regression suite, `git diff --check`, and strict runtime all pass.
8. Rollback is demonstrated by disabling NATS and continuing on REST.

## 10. Audit conclusion

The repository is not at the v3.0 distributed end state, but it has a verified v2.5-compatible baseline and a durable PostgreSQL event boundary suitable for the first reversible transport step. v3.0.0 is complete as a factual contract phase. v3.0.1 is authorized only as a **local, loopback, JetStream-backed shadow path**; it must not change the source of truth, remove REST, or imply that the powered-off VMs are online.
