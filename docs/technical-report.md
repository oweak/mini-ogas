## 1. 系统简介

Mini-OGAS 是一个面向离散制造车间的分布式工业运行管理演示系统。它不是单纯的数据看板，而是试图把主机端调度、子节点工况模拟、心跳采集、异常诊断、自动处置、人工审批、处置日志和前端交互组织成一个闭环。系统名称中的 OGAS 借用了“统一自动化管理系统”的思想，但当前实现更加贴近小型工厂、教学演示和云边协同实验环境：一个中心服务负责统一管理，多个节点负责模拟车间设备和产线状态，前端负责把实时运行、风险、计划、审批和结果直观展示出来。

系统的核心目标是减少人工在常规问题上的反复操作。正常运行时，系统通过节点心跳持续获得设备状态、生产节拍、质量指标、工单进度、能源消耗和异常信号；出现轻量问题时，由规则脚本和 AI 诊断共同给出处置建议，并在可控范围内自动执行；出现会影响安全、设备寿命、产量计划或质量风险的重大问题时，系统将问题升级到人工审批队列，由管理员或车间主管确认后再执行隔离、停机、派工、重排产或恢复指令。

从演示价值看，Mini-OGAS 的重点不是展示一个静态页面，而是展示“系统正在运行”。因此报告中的评价标准也围绕运行性展开：后端是否持续接收状态，前端是否由后端状态驱动，节点是否能产生多样化工况，AI 是否真正参与诊断，审批是否能改变系统状态，日志是否能追溯问题和处置结果。一个工业管理系统的可信感来自这些连续动作，而不是来自单个漂亮组件。

## 2. 总体系统架构

当前系统采用中心主机加多个子节点的分布式架构。中心主机运行 central-api 服务和 dashboard 前端，子节点运行 node-agent 模拟器。每个节点代表一个车间、设备组或边缘计算单元，例如 turning-workshop、milling-workshop、grinding-workshop 等。节点通过周期性心跳将当前状态提交给中心，中心聚合这些状态后形成管理视图、告警队列、调度建议和审批任务。

架构可以分为五层：第一层是模拟生产层，由节点代理生成设备传感器、工单进度、质量波动和故障事件；第二层是通信采集层，由心跳接口和节点状态缓存负责接收数据；第三层是决策控制层，由规则引擎、AI 诊断接口、调度计算和审批逻辑组成；第四层是数据持久层，用于保存节点本地状态、中心日志、诊断记录和处置记录；第五层是人机交互层，也就是 dashboard 页面，用来给管理员呈现系统运行态和必要的决策入口。

系统没有把所有逻辑堆在前端。前端的职责应该是订阅、展示和触发操作；真正的状态判断、处置生成、审批流转和日志写入应该放在 central-api。这样做有两个好处：其一，多个前端或脚本入口可以共享同一套真实状态；其二，当用户刷新页面或换浏览器时，系统状态不会凭空消失。对于工业系统而言，前端只是操作台，不应该成为事实来源。

在部署形态上，中心服务可以运行在本机，也可以运行在云服务器；子节点可以运行在本机多个进程、VirtualBox 虚拟机、云服务器实例或以后真实工控边缘盒子上。当前项目更适合使用本机加虚拟机的实验部署，因为它可以在云服务器到期或网络不稳定时继续演示完整链路，同时又能模拟多个独立节点的运行环境。

## 3. 核心运行链路

第一条链路是心跳链路。node-agent 每隔固定时间向 central-api 发送心跳，心跳内容包含节点编号、设备清单、工单状态、传感器值、OEE、告警、脚本处置结果和节点健康状态。central-api 接收后更新 node_heartbeats，并根据心跳判断是否出现新问题、旧问题是否恢复、节点是否离线以及是否需要触发告警。前端 dashboard 通过轮询 dashboard-state 等接口取得聚合状态。

第二条链路是问题处置链路。节点上报异常后，中心先按规则识别异常类型，例如主轴温度过高、冷却液流量过低、质量漂移、刀具磨损、振动过高、同步压力异常等。对于低风险问题，系统可以生成脚本处置或自动调整建议；对于高风险问题，中心创建 escalation 记录，等待人工确认。用户点击确认、隔离、升级人工处理或派遣维修后，后端必须修改对应问题状态，并将结果写入日志。

第三条链路是 AI 诊断链路。系统将节点状态、告警上下文、工单约束、设备影响和历史处置记录整理成诊断请求，调用配置好的模型接口。模型返回原因分析、风险级别、可选处置方案和建议动作。系统不能只把 AI 做成问答窗口，而应把它嵌入异常处置、调度重排、派工建议和日志说明中。AI 的输出也不能直接无条件执行，必须根据风险级别进入自动执行或人工确认分支。

第四条链路是调度链路。中心根据当前工单、设备可用性、瓶颈工序、阻塞任务和质量风险重新计算生产计划。当前前端中“重新计算计划”和“批准调度变更”的按钮必须对应后端接口，接口应返回新的计划、受影响工单、约束原因、预期效果和是否需要主管确认。审批完成后，中心将调度指令下发给相关节点，并在节点下一次心跳中反馈执行状态。

第五条链路是日志与审计链路。每一次告警生成、AI 诊断、自动处置、人工确认、派工停机、调度批准和恢复正常都应写入中心日志。日志不仅用于演示“发生了什么”，也用于证明系统闭环存在。尤其是自动处置完成后，系统应弹窗告知管理员“已处理、处理依据、影响范围、恢复指标、后续观察窗口”。

## 4. 后端 central-api 模块特性

central-api 是系统的主控层，推荐使用 FastAPI 实现。FastAPI 适合此类系统的原因在于它同时具备轻量、类型友好、接口文档自动生成和异步扩展能力。当前项目中的后端接口承担认证、状态聚合、心跳接收、AI 诊断、告警列表、工单调度、人工升级、审批决策和日志查询等职责。

认证模块负责管理员登录、AI 密钥预加载和运行时权限判断。用户之前提供的 API Key 不应直接写在普通源码里，因此系统使用加密 vault 文件保存，启动时只加载密文，管理员登录后用统一密码解锁。这样既能满足演示时“登录后才启用 AI”的需求，也避免把密钥暴露在前端包、Git 历史或普通配置文件中。

心跳模块是后端最重要的事实入口。它接收来自各节点的 Heartbeat 数据，并维护每个节点的最近状态。心跳状态不仅用于显示在线或离线，还用于判断异常持续时间、设备恢复情况、节点是否执行了中心指令、生产数据是否有同步滞后。若某节点超过阈值未上报，中心应标记为 stale 或 offline，并触发连接类告警。

告警模块将节点原始异常转化为管理系统可处理的问题对象。一个问题对象至少应包含 issue_id、节点编号、设备编号、告警类型、严重等级、当前值、阈值、触发时间、状态、建议动作、是否需要人工、处置历史和恢复条件。这样前端才能针对不同问题显示不同入口，而不是所有问题都只出现一个不能选择的警告框。

AI 模块的职责不是替代全部规则，而是补充规则在复杂场景中的判断能力。例如规则能快速判断主轴温度超过阈值，但 AI 可以综合最近负载、冷却液流量、刀具磨损、工单材质和历史趋势，给出“继续运行五分钟观察”“降低进给并补液”“立即停机派工”“隔离节点并重排工单”等差异化方案。后端应保存 AI 输出的原文摘要、模型名称、置信度或质量标签、调用状态和失败回退原因。

审批模块承担人工决策闭环。人工确认不是一个前端按钮的视觉状态，而是后端状态机的一次转移。例如 waiting_human 的问题在主管批准“派工停机修理”后，应变为 approved 或 executing，随后生成维修任务、更新设备状态为 maintenance 或 isolated，并把调度系统中的相关产能临时下线。处理完成后再变为 resolved，并记录恢复指标。

调度模块负责把工单从“静态列表”变成可计算计划。它需要维护工单优先级、工艺路线、设备能力、预计工时、截止时间、阻塞原因和资源约束。当设备出现热故障、砂轮磨损或质量漂移时，调度模块应重新计算可行计划，并说明牺牲了什么、保护了什么、需要谁审批。

## 5. 前端 dashboard 模块特性

dashboard 是系统的人机交互层，应当体现工业系统的“运行中”特征。页面不能只是卡片堆叠，而应包含实时状态、节点树、告警流、审批队列、工单计划、AI 诊断解释、处置结果、日志时间线和系统健康状态。用户打开页面后，应能直观看到哪些节点在线、哪些设备生产、哪些工单阻塞、哪些问题自动处理、哪些事项等待人工确认。

左上角系统名称保持英文，可以维持 Mini-OGAS 或 MiniOGAS。其余组块和功能入口应使用中文，降低演示对象理解成本。工业管理系统的页面语言应直接、动作明确，例如“节点运行树”“告警队列”“AI 诊断”“待人工决策”“调度计划”“处置日志”“系统健康”。不要把关键动作藏在含糊文案里。

前端必须由后端状态驱动。之前出现过后端模拟已经进入高温故障，但前端没有收到主轴温度告警的情况，这说明页面和接口之间的绑定比单个异常更重要。正确做法是 dashboard 定时请求后端聚合状态，所有告警、按钮、弹窗、节点状态和调度建议都从后端响应生成。前端本地可以保留动画状态和选中状态，但不能自行虚构事实。

告警弹窗应有进入动画、退出动画和状态变化动画，但动画只是增强认知，不应掩盖操作入口。每个弹窗至少要提供关闭、查看详情、确认收到、AI 诊断、执行建议动作或升级人工等路径。关闭弹窗不等于解决问题，只能表示管理员已知晓；真正解决必须触发后端 action，并等待后端返回执行结果。

处置完成后，前端应立即呈现反馈。反馈内容包括执行动作、影响设备、恢复指标、日志编号、后续观察时间和是否需要人工复核。页面上对应的告警卡片应从 active 移至 resolved 或 history，节点树上的状态颜色应恢复正常，日志面板应新增记录。这样用户才会感觉系统确实运行，而不是按钮按了没有效果。

节点树是前端重要组件。父节点代表中心主机或车间，子节点代表虚拟机节点，叶子节点代表设备或工序。每个节点可以显示在线状态、最近心跳、OEE、告警数、正在执行工单和控制状态。点击节点后，右侧详情显示该节点的传感器、工单、告警、AI 建议、历史处置和可下发命令。

调度区域应让“批准调度变更”具备真实入口和效果。点击批准后，前端应调用后端审批接口，后端更新计划状态并返回影响摘要；前端随后刷新计划表，把阻塞任务变更为已重排、待执行或已下发。若审批失败，应明确显示失败原因，例如权限不足、节点离线、设备仍在故障、工单约束冲突。

## 6. node-agent 子节点模拟器特性

node-agent 用于模拟真实车间边缘节点。每个节点应有自己的设备列表、工单队列、传感器状态、故障概率、处置脚本和本地日志。节点不是简单随机数发生器，而应模拟生产过程中的连续性：温度随负载上升，冷却不足会放大热风险，刀具磨损会影响质量，振动异常可能和转速、夹具或材料有关，设备停机后产量会下降，维修完成后指标逐步恢复。

为了让模拟更科学，节点应引入工艺约束和物理趋势。比如车削节点的主轴温度不能每秒完全随机跳变，而应根据负载、环境温度、冷却液流量和散热系数缓慢变化；质量漂移不应孤立出现，而可能与刀具磨损、材料批次或补偿参数有关；OEE 不应手写固定数值，而应由可用率、性能率和良品率组合计算。

节点可以使用 SQLite 保存本地状态。这样即使节点进程重启，也能保留最近工单、告警历史和执行结果。对于虚拟机部署，每台虚拟机运行一个或多个 node-agent，使用不同的 node_code 和端口配置。中心主机通过心跳识别这些节点，并根据节点上报能力给它们分配工单。

节点还应支持接受中心指令。中心下发的命令包括降低速度、暂停工单、隔离节点、恢复生产、派工维修、修改工单优先级、执行抽检任务等。节点收到命令后，不应只返回 success，而要改变本地模拟状态，并在之后的心跳中反馈执行中、完成、失败或等待人工。

当前演示环境可以先用虚拟机模拟多个节点。虚拟机的价值在于隔离环境、模拟网络延迟、模拟节点掉线、独立运行进程和更接近真实边缘部署。即使云服务器到期，本机虚拟机仍可支撑完整的中心主机加多节点演示。后续若接入真实设备，只需要把 node-agent 的模拟数据源替换为真实 PLC、OPC UA、Modbus 或数据库接口。

## 7. AI 诊断与决策参与

AI 是 Mini-OGAS 的亮点，但必须明确它到底做了什么。AI 不应只是一个问答框，也不应只是把规则结果换一种说法。它应参与至少四类任务：异常原因分析、处置方案生成、调度重排解释、处置结果总结。每次 AI 参与都应在页面上留下可见痕迹，包括输入上下文摘要、模型返回建议、系统采用或未采用的原因。

在异常诊断中，AI 接收的数据应包括节点状态、设备当前值、阈值、最近趋势、工单类型、历史异常、可用处置动作和风险约束。AI 输出应包含“可能原因”“建议动作”“风险说明”“是否需要人工确认”“预期恢复指标”。例如主轴温度过高时，AI 可以建议先降低进给和检查冷却，如果温度继续上升则派遣工人停机维修；如果同时存在冷却液流量不足，则建议优先检查泵和管路。

在调度场景中，AI 可用于解释重排计划，而不直接替代优化算法。算法负责计算可行计划，AI 负责把结果转化为人能理解的说明，例如为什么把阻铁削产量从 MILL-02 转移到 MILL-01，为什么保留 GRIND-01 的精加工能力，以及这个动作对交付时间、质量风险和设备恢复有什么影响。

AI 接口应真实接入模型服务，但系统必须承认外部 API 存在失败、超时、模型名不可用、额度不足或网络波动。后端应清楚区分 live、recorded、fallback、api_error 等状态。若模型调用失败，可以使用规则回退，但页面必须标注“规则回退”而不是假装 AI 已成功调用。这样系统才可信。

安全边界也很重要。AI 给出的建议不能越过后端权限和审批规则。对于低风险脚本动作，系统可以自动执行；对于停机、隔离、派工、调度变更、产量调整等影响生产的动作，AI 只能建议，必须进入人工确认或主管审批。审批之后，由后端动作接口执行并写日志。

## 8. 人工确认与审批机制

工业系统中的人工确认不是装饰按钮，而是风险控制机制。系统应把问题分为自动处理、需要确认、需要主管批准、必须人工现场处理四类。自动处理的问题可以由脚本执行，但执行后必须通知人；需要确认的问题由操作员选择执行方案；需要主管批准的问题进入审批队列；必须现场处理的问题应生成派工建议和停机隔离建议。

针对主轴温度过高这类物理问题，系统不应只提供“关闭警告”。更合理的路径是：第一步确认告警，第二步查看 AI 诊断，第三步选择处置方案，例如降低转速观察、暂停当前工单、派遣工人检查冷却系统、停机维修、隔离节点并重排工单。每个动作对应一个后端接口，执行后状态变化应反映到设备、工单和日志。

审批记录需要可追溯。每条审批应记录审批人、时间、原问题、AI 建议、人工选择、执行命令、执行结果和恢复状态。这样演示时可以回答“谁批准了调度变更”“为什么停了这台车床”“AI 建议是否被采用”“处理后是否恢复正常”等问题。

前端的待人工决策队列应避免重复堆积同一问题。若同一节点同一设备持续上报同一异常，系统应该合并为一个活动问题，并更新持续时间和最近值，而不是每次心跳都生成一张新卡片。处理完成后，队列移除该问题，并把完整记录送入日志。

## 9. 工单与调度设计

工单数据由主机端统一创建和分发给子节点。每个工单应包含工单编号、产品类型、工艺路线、目标数量、已完成数量、截止时间、优先级、质量要求和可用设备约束。中心根据节点能力和当前状态分配工单，节点只执行被分配的任务并上报进度。这样系统的组织逻辑更接近真实工厂，而不是每个节点各自生成无关任务。

调度模块应支持动态重排。生产过程中设备故障、质量漂移、工序阻塞、节点掉线都会改变原计划。系统应根据实时状态计算新的计划，并给出重排理由。对于影响产量或设备状态的变更，必须进入“批准调度变更”流程。批准后，后端更新调度计划并下发给节点，节点反馈执行结果。

为了提高集成性，调度界面不能让人手忙脚乱。它应该把关键内容集中呈现：当前阻塞点、建议动作、受影响工单、需要审批的人、预计恢复时间和备用产能。用户不需要在多个页面寻找信息，而是在同一工作台完成查看、诊断、批准、执行和复核。

系统可将调度和 AI 结合：调度算法计算方案，AI 解释方案并提示风险。比如 MILL-02 热故障时，算法建议把部分工单转移给 MILL-01，AI 则说明为什么不能全部转移、为什么需要保留 GRIND-01 精加工能力、预计会对某个截止时间产生多少风险。

## 10. 系统配置说明

系统配置分为中心主机配置、前端配置、节点配置、AI 配置和虚拟机配置。中心主机需要设置 API 监听地址、端口、允许跨域来源、日志目录、数据库路径、心跳超时阈值和管理员密码策略。前端需要设置后端 API 地址、刷新间隔、登录跳转、动画开关和演示模式。节点需要设置 node_code、central_url、heartbeat_interval、设备清单、模拟参数和本地 SQLite 路径。

AI 配置应保存在加密文件中，而不是写入源码。加密文件可以包含 provider、base_url、model、api_key_ciphertext、salt、nonce、校验摘要等字段。系统启动时只检测文件存在和格式，不解密密钥；管理员登录后输入密码，后端解锁并把密钥保存在运行时内存中。前端永远不应接触明文 API Key。

虚拟机配置建议放在 D 盘独立目录，例如 D:\miniogas-lab，用来保存虚拟机镜像、节点配置、启动脚本和日志。每个虚拟机可以运行同一份 node-agent 代码，但使用不同配置文件。中心主机通过内网地址或 NAT 端口接收节点心跳。若本机资源有限，可以先运行 3 到 5 个节点；若内存充足，可以扩展到更多节点。

一键部署脚本应统一完成依赖检查、目录创建、Python 虚拟环境、Node 依赖、中心 API 启动、前端启动、节点配置生成和虚拟机节点启动。脚本必须输出清晰的地址和状态，例如 central-api 地址、dashboard 地址、已启动节点数、失败节点和日志路径。

## 11. 语言使用与应用

Python 是后端和节点模拟器的主要语言。它适合快速实现 API、数据模型、模拟算法、文件处理、AI 接口调用和部署脚本辅助逻辑。FastAPI 与 Pydantic 可以用类型模型描述请求和响应，减少接口字段混乱。SQLite 与 Python 标准库可以支撑轻量本地存储。对于工业演示系统，Python 的开发速度和生态便利性很高。

TypeScript 或 JavaScript 是前端 dashboard 的主要语言。前端负责页面状态、接口请求、组件渲染、动画、用户操作和可视化。若使用 Vue，推荐通过组合式 API 管理状态，通过组件拆分节点树、告警队列、诊断面板、审批队列和日志流。前端语言的重点不是复杂算法，而是把后端真实状态组织成清晰的交互。

PowerShell 用于 Windows 本机部署和运维。由于用户环境在 Windows，PowerShell 适合编写一键启动、虚拟机创建、进程检查、端口检查、日志查看和依赖安装脚本。脚本应避免破坏性操作，创建目录和启动服务前应输出明确提示。

Markdown 用于技术文档、部署说明和报告。Markdown 易读、易维护、便于版本管理，也可以转换为 Word。Word 文件适合提交、汇报和打印，因此本报告同时生成 Markdown 与 DOCX 两份。

JSON 用于配置、API 请求响应和加密 vault 元数据。JSON 结构清晰，适合前后端共享，但不能用普通 JSON 保存明文密钥。对于节点配置，JSON 或 TOML 都可以；对于更复杂的生产配置，后续可以迁移到数据库或配置中心。

## 12. 技术使用与应用

FastAPI 用于构建 REST API。它的自动文档、类型验证和异步能力适合中心主机服务。接口应围绕业务动作设计，而不是围绕前端组件设计。例如 /api/node-heartbeats 代表节点上报，/api/dashboard-state 代表前端聚合状态，/api/ai/diagnose 代表诊断请求，/api/ops/escalations/{id}/decision 代表人工审批决策。

Pydantic 用于定义数据模型。Heartbeat、DiagnoseRequest、EscalationDecision、DispatchApproval 等模型可以保证字段类型一致。这样节点、后端和前端之间的契约更稳定，也方便未来生成 OpenAPI 文档和前端类型。

SQLite 用于轻量持久化。节点端可用 SQLite 保存本地工况、工单、告警和执行记录。中心端也可以先用内存结构加日志文件演示，后续再迁移到 SQLite、PostgreSQL 或 TimescaleDB。若需要存储大量传感器时序数据，专用时序数据库会更合适。

Vue 用于构建 dashboard。Vue 的响应式机制适合处理轮询状态、局部刷新和组件联动。节点树点击后更新详情面板，告警状态变化后自动触发动画，审批完成后刷新队列，这些都适合通过响应式状态实现。

VirtualBox 或类似虚拟化工具用于模拟多节点。每台虚拟机代表独立边缘环境，能够测试网络故障、节点离线、资源隔离和多节点心跳。相比全部运行在同一进程中，虚拟机更接近真实部署，但资源消耗更高。

AI API 用于诊断和解释。系统应通过后端调用模型服务，并设置超时、重试、错误分类和回退策略。AI 调用结果应可审计，不能只在前端临时显示。若模型服务不可用，系统可回退到规则引擎，但必须如实显示。

## 13. 数据模型与状态机

节点状态模型包含 node_code、display_name、online、last_heartbeat、health、oee、active_orders、devices、alerts、commands 和 logs。设备模型包含 machine_id、type、state、temperature、vibration、coolant_flow、tool_wear、quality_rate、current_order 和 maintenance_state。工单模型包含 order_id、product、route、quantity、completed、deadline、priority、assigned_node 和 status。

问题状态机建议使用 active、acknowledged、diagnosing、waiting_human、approved、executing、resolved、dismissed、failed 等状态。active 表示问题刚出现；acknowledged 表示管理员已知晓；diagnosing 表示 AI 或规则正在分析；waiting_human 表示需要人确认；approved 表示人已批准动作；executing 表示命令下发执行中；resolved 表示恢复；dismissed 表示用户关闭但未处置；failed 表示处置失败。

调度状态机建议使用 planned、running、blocked、recalculating、waiting_approval、approved、dispatched、completed 等状态。一个工单在设备故障时可能从 running 变成 blocked，重排后进入 waiting_approval，批准后变为 dispatched，节点确认后回到 running。前端每个状态都应该有明确颜色和动作入口。

日志模型应覆盖事件时间、事件来源、节点、设备、工单、事件类型、严重等级、操作人、AI 诊断编号、动作编号和结果。日志不只是文本列表，而是系统行为证据。演示中如果有人问某个问题如何处理，日志应能追溯完整链路。

## 14. 系统特性总结

第一，系统具备分布式模拟特性。中心主机与多个节点通过心跳连接，节点可以运行在本机进程、虚拟机或云服务器上。第二，系统具备实时管理特性。前端周期性获取后端状态，展示节点在线、生产状态、告警和调度变化。第三，系统具备智能诊断特性。AI 接口参与问题分析和调度解释，但受规则和人工审批约束。

第四，系统具备闭环处置特性。异常从发现、诊断、确认、执行到恢复和日志记录形成完整链路。第五，系统具备工业演示特性。主轴温度、冷却液、刀具磨损、质量漂移、振动等问题比单一随机告警更接近真实车间。第六，系统具备扩展特性。未来可以接入真实 PLC、OPC UA、MES、ERP、仓储系统和人员排班系统。

第七，系统具备可审计特性。AI 诊断、人工审批、自动处置和调度变更均可记录。第八，系统具备安全边界。AI 不直接执行高风险动作，密钥不暴露在前端，人工确认用于关键生产决策。第九，系统具备部署灵活性。云服务器、本机和虚拟机都可作为不同角色参与。

## 15. 模块特性汇总

central-api 模块的关键特性是统一事实源、接口聚合、状态机管理、AI 调用、审批执行和日志审计。它决定系统是否真实运行。若 central-api 只返回静态数据，前端再精美也无法成为工业系统。

dashboard 模块的关键特性是可视化运行态、交互闭环和反馈明确。它应让管理员快速理解发生了什么、系统建议什么、哪些动作已自动完成、哪些动作需要人工决定。

node-agent 模块的关键特性是模拟真实生产过程。它应持续生成有物理连续性的工况，并能响应中心下发的命令。节点不是背景数据源，而是整个系统运行感的基础。

deployment 模块的关键特性是一键化和可复现。它应减少用户手工启动多个服务的负担，尤其是在多虚拟机环境下，统一脚本能显著降低演示失败概率。

docs 模块的关键特性是说明系统设计、部署方式、接口约束和演示流程。对于一个需要展示给他人的系统，文档本身也是可信度的一部分。

## 16. 技术知识详解

心跳机制是分布式系统常见技术。节点按固定周期向中心发送状态，中心用最近一次心跳时间判断节点是否在线。心跳不只是 ping，而是携带业务状态的数据包。工业场景中，心跳频率需要权衡实时性和网络负载。过慢会导致告警滞后，过快会增加服务压力。

状态机是管理复杂流程的基础。告警、审批、工单和调度都应该用明确状态流转，而不是用多个布尔值拼凑。状态机可以避免逻辑混乱，例如一个已解决的问题不应再次等待人工确认，一个未审批的调度不能被标记为已下发。

规则引擎适合处理确定性条件。例如温度超过阈值、节点离线超过时限、良品率低于下限、心跳延迟超过标准等。规则引擎的优点是可解释、稳定、速度快；缺点是面对多因素耦合问题时不够灵活。

AI 诊断适合处理上下文综合。它可以把多个指标和自然语言约束组织成方案，但必须受到系统规则限制。工业系统中不能把模型输出视为绝对事实，而应视为决策建议。系统需要记录模型输入摘要、输出摘要、采用情况和回退原因。

虚拟化技术用于在单台物理机上运行多个独立环境。对于 Mini-OGAS，虚拟机可模拟多个车间节点，每个节点有独立 IP、进程、日志和故障。虚拟机比普通进程更稳定地模拟边缘节点，但会消耗更多 CPU、内存和磁盘。

API 设计需要关注幂等性和可追溯性。确认告警、批准调度、执行隔离等动作可能被重复点击或网络重试，因此后端应避免重复生成相同结果。每个动作最好返回 action_id 或 log_id，方便前端显示和后续查询。

日志审计是工业系统的重要能力。日志应覆盖自动动作和人工动作，并且不能只保存在前端。一个可信系统需要回答何时发生、谁处理、为什么处理、处理后怎样。

安全配置需要避免明文密钥。API Key 应保存在加密文件中，解锁后只留在后端内存。前端如果能看到密钥，就意味着任何浏览器用户都可能复制密钥，这不符合安全要求。

## 17. 语言知识详解

Python 的优势在于生态和表达效率。FastAPI、requests、sqlite3、pydantic、python-docx 等库可以快速完成后端、模拟器和文档生成。Python 代码应注意类型模型、异常处理、超时控制和日志输出。工业系统即使是演示版，也不应让异常静默失败。

JavaScript 和 TypeScript 的优势在于浏览器端交互。它们负责动态页面、按钮响应、动画、图表和状态刷新。TypeScript 相比 JavaScript 更适合大型前端，因为它能在编译阶段发现字段名和类型错误。当前系统若继续扩展，建议逐步加强类型定义。

Vue 的核心知识包括组件、响应式状态、生命周期、计算属性和事件处理。dashboard 可以拆分为 NodeTree、AlertQueue、AiDiagnosisPanel、DispatchPlan、ApprovalQueue、AuditLog 等组件。拆分后每个组件只关心自己的显示和操作，整体更容易维护。

PowerShell 的核心知识包括路径处理、进程管理、环境变量、执行策略和管道。Windows 部署脚本需要特别注意路径中空格，例如 C:\Users\hq362\Documents\New project。脚本中引用路径应使用引号或 LiteralPath。

Markdown 的核心知识包括标题层级、列表、代码块、表格和链接。技术报告用 Markdown 编写可以方便后续版本控制和自动转换。Word 则更适合正式提交。两者内容应来自同一份源，避免版本不一致。

## 18. 系统现状与风险

当前系统已经具备中心服务、前端展示、节点模拟、AI 配置、告警处置和调度审批的基本方向，但仍需要严格检查前后端是否完全连通。用户指出的问题很关键：若后端已经进入高温故障，而前端没有告警；若按钮没有真实效果；若人工确认没有入口；若 AI 诊断看不到具体诊断内容，那么系统就仍像静态前端，而不是运行中的管理系统。

另一个风险是 AI 调用真实性。系统可以配置 DeepSeek 或其他模型接口，但必须在页面和日志中区分真实调用、录制结果和规则回退。只要外部 API 超时或模型名不可用，就不能声称 AI 成功参与。正确做法是如实显示调用状态，并把失败时的回退路径作为系统韧性的一部分。

第三个风险是重复告警和重复审批。如果每次心跳都生成新告警，队列会很快堆满，用户无法判断真实问题数量。后端应通过 issue_id 或相似性规则合并持续问题。第四个风险是处置效果不可见。任何按钮按下后，都必须有后端状态变化和前端反馈，否则用户会认为系统没有支撑。

第五个风险是模拟科学性不足。如果工况只是随机数，系统看起来会不真实。后续应加入更明确的物理趋势、工艺约束、故障传播和恢复曲线。演示时最有说服力的不是异常很多，而是异常之间有因果关系，处置之后指标按合理路径恢复。

## 19. 后续建设建议

第一，建立统一事件总线。所有告警、诊断、审批、调度和恢复都写入同一事件流，前端从事件流和聚合状态中展示系统运行。第二，完善节点树。节点树应成为主导航，用户点击任何节点都能看到当前状态、问题、工单和可执行动作。

第三，完善 AI 可见性。AI 面板应显示诊断输入摘要、原因分析、建议方案、风险等级、模型调用状态和是否采用建议。第四，完善人工审批。每个 waiting_human 或 waiting_approval 状态都必须有入口、按钮、结果反馈和日志。

第五，完善模拟器。加入多类故障、趋势模型、恢复模型、命令响应和本地持久化。第六，完善部署脚本。脚本应支持一键启动中心、前端和指定数量节点，并能检查节点是否真正上线。

第七，完善测试。至少需要接口测试、状态机测试、节点心跳测试、AI 回退测试和前端端到端测试。特别要测试“后端产生异常后前端必须出现告警”“人工批准后状态必须改变”“处置完成后日志必须新增”这些关键链路。

## 20. 系统配置清单建议

中心主机建议配置：CPU 2 核以上、内存 4GB 以上、Python 3.11 或更高、Node.js 18 或更高、可用端口 8000 和前端开发端口。若同时运行多个虚拟机，建议内存 16GB 以上。

虚拟机节点建议配置：每个节点 1 核 CPU、512MB 到 1GB 内存、最小 Linux 系统、Python 运行环境、node-agent 配置文件和到中心主机的网络访问。演示时可先运行 3 个节点，分别模拟车削、铣削和磨削车间。

网络配置建议：中心主机固定局域网地址，节点配置 central_url 指向中心 API。若使用 NAT，需要做好端口映射。心跳间隔建议 3 到 10 秒，离线判定建议为 3 到 5 个心跳周期。

安全配置建议：管理员密码不应硬编码在前端。AI vault 使用密码解锁，密钥不进入 Git。日志中禁止写入完整 API Key。生产环境还需要 HTTPS、访问控制、审计账号和密钥轮换。

## 21. 结论

Mini-OGAS 的正确方向是把它做成一个真正运行的工业管理系统演示，而不是静态大屏。它需要中心主机掌握事实，节点持续模拟生产，前端实时反映状态，AI 参与诊断和解释，人工负责关键决策，日志记录每一次动作。只有这些链路闭合，系统才会有工业管理的可信感。

当前技术栈适合继续推进：Python 与 FastAPI 负责后端和模拟，Vue 负责 dashboard，PowerShell 负责 Windows 部署，虚拟机负责多节点环境，AI API 负责诊断增强。后续重点不是堆更多页面，而是确保每个按钮都有后端效果，每个异常都有处置路径，每个处置都有恢复反馈，每个 AI 建议都能被看见、被采用或被拒绝。

这份报告同时提供 Markdown 和 Word 两种格式。Markdown 适合后续迭代维护，Word 适合提交和展示。报告内容可作为后续开发清单、答辩材料和系统说明书的基础。

## 22. 附录A：典型异常处置流程

主轴温度过高流程：节点上报 LATHE-01 温度持续超过阈值，中心创建高风险问题；AI 综合负载、冷却液、转速和历史趋势给出建议；若建议停机维修，前端弹窗显示原因和可选动作；操作员确认派工后，后端将设备状态改为 maintenance，调度模块移除该设备产能，节点收到命令后停止工单并反馈执行；维修完成后节点温度回落，中心标记 resolved，日志记录完整过程。

质量漂移流程：节点上报良品率下降但未达到停机阈值，中心先允许脚本执行轻量补偿，例如调整刀补或增加抽检；AI 判断若漂移继续恶化则升级人工。处置成功后，前端显示“自动处置完成”，并把良品率恢复趋势写入日志。若连续多个周期未恢复，则进入人工决策。

冷却液流量不足流程：节点检测流量低于阈值，系统建议检查泵、过滤器和管路。若问题轻微，节点可执行降低负载和提醒补液；若同时伴随主轴温度升高，系统应提升风险等级，建议停机派工。

振动过高流程：节点上报振动异常，AI 结合转速、夹具、刀具和工件信息判断可能原因。低风险时建议降低转速并观察；高风险时建议暂停设备，避免轴承或夹具损坏。

## 23. 附录B：接口设计建议

/api/dashboard-state 返回系统聚合状态，包括节点树、告警队列、审批队列、工单计划、AI 状态和最近日志。这个接口是前端主刷新入口。/api/node-heartbeats 接收节点心跳，由 node-agent 调用。/api/ai/diagnose 接收诊断请求，由前端或后端问题流程触发。

/api/issues/{issue_id}/actions 用于执行具体处置动作，例如 acknowledge、dispatch_worker、isolate_node、reduce_speed、resolve、dismiss。接口返回 action_id、new_status、message 和 log_entry。/api/ops/escalations/{id}/decision 用于人工审批，必须改变 escalation 状态。/api/ops/dispatch-plan/approve 用于批准调度变更，必须改变计划和工单状态。

接口响应应统一包含 ok、data、error、request_id 和 timestamp。失败时 error 应包含 code、message 和 detail。前端根据 code 显示明确提示，而不是只显示操作失败。

## 24. 附录C：演示脚本建议

正常运行演示：启动中心 API、前端和多个节点，打开 dashboard，展示节点树全部在线，工单持续推进，OEE 和质量指标随时间变化。强调系统不是静态页面，而是由节点心跳驱动。

异常诊断演示：触发 LATHE-01 主轴温度过高，观察弹窗动画、告警队列新增、AI 诊断内容出现、节点树变色。选择派工停机修理，查看设备状态、调度重排和日志变化。

调度审批演示：触发 MILL-02 热故障，点击重新计算计划，系统展示建议动作和影响工单。点击批准调度变更，前端刷新计划状态，日志记录主管批准。

AI 透明性演示：打开 AI 诊断详情，展示模型名称、调用状态、原因分析和建议。如果外部 API 不可用，展示规则回退，并说明系统不会假装模型成功。

## 25. 附录D：测试重点

接口测试应覆盖心跳接收、dashboard 聚合、告警生成、AI 诊断、人工审批、调度批准和日志查询。状态机测试应覆盖重复告警合并、已解决问题不再审批、审批后状态更新、失败动作进入 failed。前端测试应覆盖按钮是否可点击、点击后是否调用接口、接口返回后页面是否改变。

端到端测试应模拟一个完整场景：节点上报高温，前端出现告警，用户点击 AI 诊断，用户批准停机维修，节点收到命令，心跳反馈执行，系统恢复正常，日志出现完整记录。这个测试比单独检查页面样式更有价值。

## 26. 附录E：项目评价标准

判断 Mini-OGAS 是否像真实工业系统，可以用六个问题检验：第一，数据是否来自持续运行的节点；第二，前端是否由后端状态驱动；第三，异常是否有多类型和因果关系；第四，AI 是否产生可见诊断和建议；第五，人工确认是否真正改变系统状态；第六，处置完成后是否恢复并写入日志。

若这六个问题都能回答是，系统就已经具备可信演示基础。若其中任何一个为否，就会被用户感受到“像静态前端”。因此后续开发应始终围绕闭环，而不是只增加装饰。
