## 一、系统简介

### 1.1 项目背景

Mini-OGAS 是一个面向**分布式机械加工工厂**的制造执行系统（MES），其名称来源于苏联控制论学家维克托·格卢什科夫在 1960 年代提出的"全国自动化系统"（OGAS — All-State Automated System）概念。本项目取其分布式管控、中心化协调的核心理念，将 OGAS 思想应用到一个中小型机械加工工厂的实际生产管理中。

系统由一个**中央控制节点**（Central API）、多个**车间边缘节点**（Workshop Node Agents）、**AI 诊断引擎**、**市场模拟器**、**生产计划器**以及一个 **Web 工业控制台**（Dashboard）组成。整个系统通过 HTTP REST API 进行实时通信，并预留了 NATS 消息总线的集成能力。

核心设计哲学：**"AI + 脚本自动处置为主，人工决策为辅"**——系统设计追求尽可能减少人工操作：大部分小型问题由预设脚本和 AI API 自动诊断并解决，处理后将日志保存并通过弹窗通知人类；只有重大决策（如节点隔离、调度重排）才由人工确认执行，且所有高风险操作必须写入审计日志。

### 1.2 系统目标

- **分布式节点管理**: 支持多个物理/云端车间节点接入，每个节点运行独立的 Agent 采集系统指标并上报
- **实时生产监控**: 以秒级频率采集各车间 CPU、内存、磁盘、网络、API 延迟等指标
- **自动故障处置**: 三级故障分类处理——L1 脚本自动修复 / L2 AI 诊断建议 / L3 自动隔离并人工确认
- **AI 辅助决策**: 集成 DeepSeek 大语言模型，提供根因分析、诊断建议、和自然语言控制指令
- **市场驱动排程**: 模拟外部市场需求变化，根据需求指数、库存压力和竞争价格动态调整生产计划
- **全链路审计追踪**: 所有报警、命令、事件、AI 诊断结果完整记录，满足合规审计需求
- **工业级控制台**: Vue 3 灰白主题单页面控制台，包含工厂拓扑、工单调度、报警处置、演示指挥四大功能区

### 1.3 适用范围

本项目当前定位为**研究生面试演示作品**，完整展示了分布式系统设计、工业物联网（IIoT）数据采集、AI 辅助运维（AIOps）、微服务架构、前后端分离开发、容器化部署等层面的工程能力。模拟场景基于真实机械加工车间的设备配置和工作流程（车削、铣削、磨削三车间），仿真数据遵循物理因果约束而非独立随机数。

### 2.3 通信与认证

**Dashboard → Central API**: 通过 Vite 开发服务器代理（开发环境）或 nginx 反向代理（生产环境）转发。所有请求携带 `X-OGAS-Token` 请求头进行身份认证。Token 值通过环境变量 `API_ACCESS_TOKEN` 配置。

**Node Agent → Central API**: 直接 HTTP 通信，使用 `NODE_INGEST_TOKEN`（默认与 `API_ACCESS_TOKEN` 相同）进行认证。Agent 每 5 秒上报指标数据，同时轮询待执行命令。

**Central API → 微服务**: 当 `MICROSERVICES_ENABLED=true` 时，central-api 通过 HTTP 调用 ai-dispatcher、market-simulator、production-planner 的健康检查和业务端点。

**Central API → DeepSeek**: 直接 HTTPS POST 到 `https://api.deepseek.com/chat/completions`，使用 `DEEPSEEK_API_KEY` 认证。同步调用（urllib），超时 25 秒。

### 2.4 数据流

```
[仿真引擎后台循环]
    │
    │ 每 ~3 秒执行 simulation_step()
    │
    ├─ 1. 车间指标随机游走 (CPU/Mem/Disk/Net/Latency/产量)
    ├─ 2. 设备磨损/负载漂移 (刀具磨损、负荷率、良品率)
    ├─ 3. 市场需求漂移 (需求指数 ±5, 价格 ±2%)
    ├─ 4. 每 10 tick 注入模拟调配订单
    ├─ 5. 每 8 tick 重算生产计划 + 重排调度
    ├─ 6. 概率性异常注入 (disk=92% L1, CPU=95%+Lat L2)
    ├─ 7. 每 20 tick AI 自动简报
    │
    ▼
[MemoryStore 内存状态]
    │
    ├─ GET /management/snapshot → Dashboard 主轮询 (1s)
    ├─ GET /alerts               → 报警页轮询 (10s)
    ├─ POST /ai/diagnose         → 用户触发 AI 诊断
    ├─ POST /ops/issue-command   → 用户触发隔离/命令
    └─ POST /ops/escalate        → 用户触发人工升级
```

## 三、模块特性

### 3.1 central-api — 中央控制 API

**核心技术栈**: Python 3.12, FastAPI 0.115, Pydantic 2.10, Uvicorn 0.34

**状态管理 (`store.py`, 1047 行)**:

- `MemoryStore` 类：整个系统的内存状态中心，包含节点、指标、报警、AI 诊断、工单、调度、市场信号、审计日志等全部数据
- 单例模式（模块级 `store` 实例），在 FastAPI 应用工厂中共享
- 可选 SQLite 持久化（5 张表：metrics, alerts, ai_diagnosis, commands, audit_logs）
- 规则引擎内嵌于 `record_metric()` 方法中

**仿真引擎**:

- 后台 `asyncio.Task` 持续运行 (`core/lifecycle.py`)
- `simulation_step()` 执行完整的一个仿真周期：指标随机游走、设备磨损、市场漂移、异常注入、定期重排、AI 简报
- 速度可调：0.2x (15 秒/tick) ~ 5.0x (0.6 秒/tick)
- 异常率可调：0% ~ 100%（默认 12%）
- 随机种子固定为 260507，确保可复现

**三级故障处理体系**:

| 级别 | 触发条件 | 严重度 | 处置方式 |
|------|---------|--------|---------|
| L1 | 磁盘使用率 ≥ 90% | low | 自动创建 `clean_temp_cache` 脚本修复命令，记录事件 |
| L2 | CPU ≥ 92% 且 API 延迟 ≥ 800ms | medium | 节点标记为 degraded，调用 DeepSeek 诊断，生成 `restart_workshop_scheduler` 待审批命令 |
| L3 | 网络入流量 ≥ 100MB/s | high | 自动隔离节点，记录 hostile-detected 事件，冻结拓扑边 |

**路由模块（13 个 Router 文件）**:

| 路由文件 | 端点数 | 职责 |
|---------|--------|------|
| `health.py` | 4 | 健康检查、汇总、主机状态、集成状态 |
| `nodes.py` | 12 | 节点 CRUD、指标上报、心跳、命令轮询、拓扑、隔离/恢复 |
| `market.py` | 2 | 市场信号、预测查询 |
| `production.py` | 5 | 库存、调配订单、生产计划生成与提交 |
| `dispatch.py` | 3 | 调度任务、资源分配、重排 |
| `ai.py` | 6 | AI 诊断记录、状态、快捷指令、诊断触发、Chat |
| `control.py` | 1 | 自然语言控制命令（关键词 + DeepSeek 双模解析） |
| `ops.py` | 6 | 待审批命令、批准/拒绝、升级、命令签发 |
| `simulation.py` | 3 | 仿真状态、控制、单步推进 |
| `demo.py` | 1 | 演示场景注入 |
| `audit.py` | 4 | 报警、命令、事件、审计日志查询 |
| `history.py` | 1 | 按节点查看指标历史 |
| `transfer.py` | 2 | 跨节点数据/文件传输测试 |

**安全中间件** (`core/security.py`):

- 基于 `X-OGAS-Token` 请求头的 Token 认证
- 跳过 `/health` 和 OPTIONS 请求
- 指标上报路径 (`/metrics`, `/api/nodes/*`) 使用独立 `NODE_INGEST_TOKEN`
- 每客户端 IP + 路径的速率限制（默认 180 次/分钟）

### 3.2 node-agent — 车间节点代理

**核心技术栈**: Go 1.23, gopsutil v4, modernc.org/sqlite

**功能模块**:

- **指标采集** (`internal/metrics/collector.go`): 通过 gopsutil 库采集宿主机真实 CPU、内存、磁盘、网络 I/O 指标，而非模拟数据
- **本地存储** (`internal/localdb/sqlite.go`): 纯 Go 实现的 SQLite（无 CGO 依赖），本地缓冲未同步的指标和告警，提供断网容灾
- **心跳上报** (`internal/heartbeat/heartbeat.go`): 每 5 秒向 central-api 发送 PUT `/api/nodes/{code}/heartbeat`，携带 Agent 版本、运行时长、本地数据库大小、节点状态
- **命令执行** (`internal/commands/executor.go`): 定时轮询 GET `/api/nodes/{code}/pending-commands`，执行后回传结果。内置命令：`clean_temp_cache`、`restart_workshop_scheduler`
- **配置管理** (`internal/config/config.go`): 环境变量驱动，支持 `NODE_CODE`、`WORKSHOP_TYPE`、`CENTRAL_API_URL` 等配置

**数据同步机制**: 本地 SQLite 表包含 `synced` 字段标记是否已上传。Agent 具备离线缓冲能力——网络中断时指标暂存本地，恢复后批量上传。

### 3.3 ai-dispatcher — AI 诊断网关

**核心技术栈**: Python 3.12, FastAPI, httpx 0.28 (async HTTP)

**诊断流程**:

1. 接收 `DiagnosisRequest`（节点代码、告警类型、严重度、描述、最近指标记录）
2. 检查 DeepSeek API Key 是否已配置
3. **DeepSeek 路径**: 通过 httpx AsyncClient 发送结构化的诊断 Prompt 到 `deepseek-chat` 模型，要求返回 JSON 格式（`response_format: {"type": "json_object"}`），含 root_cause、recommended_action、confidence、need_isolation、summary
4. **本地回退路径**: 当 DeepSeek 不可用时，按规则生成诊断——high/critical 严重度 → 建议隔离，否则建议运行脚本后观察
5. 返回 `DiagnosisResult`，标注来源（`deepseek` 或 `local-fallback`）

### 3.4 market-simulator — 市场信号模拟器

**产品目录**（独立于 central-api 的产品代码 P1-P5）:

| 代码 | 基准价格 | 模拟波动 |
|------|---------|---------|
| P1 | 120.0 | 季节性因子 0.85–1.25 |
| P2 | 180.0 | 需求指数 50–130 × 季节性 |
| P3 | 260.0 | 竞争者价格 ±10% |
| P4 | 310.0 | 库存压力 0–100 |
| P5 | 420.0 | 综合波动 |

每次 `/signals` 调用生成随机市场快照。注意：当 `MICROSERVICES_ENABLED=false`（默认）时，central-api 使用内部的 A1-A5 产品目录自行模拟市场信号。

### 3.5 production-planner — 生产计划器

**排程逻辑**:

1. 筛选健康车间：`status == "online"` 且 `load_score < 80`
2. 对每个市场信号，检查工艺路线是否可由健康车间完整服务
3. 优先级计算：`pressure = demand_index - inventory_pressure`，若 pressure > 60 且路线可用 → P2（高优），否则 → P6（常规）
4. 目标产量：路线可用时 `max(10, int(pressure * 2))`，不可用时 `max(5, int(pressure))`
5. 最终计划按优先级升序排序

注意：当 `MICROSERVICES_ENABLED=false` 时，central-api 内部做同样的计算。

## 四、系统特性

### 4.1 核心设计理念

**1. 中心化管控 + 边缘自治**

中央服务器（central-api）承担全局状态管理、仿真驱动、生产排程、AI 诊断调度的角色。每个车间节点运行独立的 Go Agent，具备本地 SQLite 缓存、离线缓冲、命令执行能力。中央与边缘通过 HTTP 心跳保持同步——网络中断时节点自主运行，恢复后自动批量上传数据。

**2. AI + 脚本双层自动化**

系统追求最小化人工干预：L1 级别问题（如磁盘空间不足）由脚本自动执行 `clean_temp_cache` 命令；L2 级别问题（如 CPU 异常高 + API 延迟）由 DeepSeek AI 给出根因分析和处置建议；只有 L3 级别（如异常流量疑似攻击）和需要隔离/停机的高风险动作才升级到人工决策。所有 AI 输出必须先写入审计日志。

**3. 仿真驱动的演示能力**

不同于传统系统的"静态数据看板"，Mini-OGAS 内置完整的仿真引擎，可在无实际车间设备的情况下，模拟 3 个车间 × 5 台设备的全流程生产运行。仿真数据遵循物理因果约束——CPU 与 API 延迟正相关、刀具磨损随产量累积增长、设备状态机防止不真实跳变——使演示更具说服力。

**4. 审计优先的权限体系**

角色-权限矩阵定义了"操作员"、"车间主管"、"审计员"、"应急响应员"四种角色的操作边界。所有高风险操作（隔离、停机、调度变更）必须由具有相应权限的角色确认，并完整写入审计日志（时序数据库 + 结构化事件记录）。

## 八、技术知识

### 8.1 分布式系统

**CAP 定理权衡**: Mini-OGAS 选择 **CP (一致性 + 分区容错)** 模型——在网络分区时优先保证中央状态一致性，节点侧通过本地 SQLite 提供可用性降级。心跳机制（5 秒间隔）作为故障检测手段。

**服务发现**: 当前采用静态配置（环境变量指定 URL），Docker Compose 环境下使用服务名作为 DNS。未来可升级为 Consul/NATS 动态发现。

**数据一致性**: 节点本地 SQLite 使用 `synced` 标志位实现最终一致性——数据先写本地，批量同步，同步后标记。网络中断期间无数据丢失。

### 8.2 工业物联网 (IIoT)

**指标采集范式**: 遵循 OPC UA / MTConnect 风格的标准化指标模型——每个采集点包含时间戳、节点标识、指标名、指标值。当前使用 HTTP 上报，可平滑迁移到 MQTT/NATS。

**设备状态机**: 设备状态转移符合工业标准：running ↔ warning ↔ fault → isolated → maintenance → running。禁止不真实跳变（如直接从 running 跳到 maintenance）。

**刀具磨损监控**: 模拟真实的刀具磨损累积曲线——磨损随产量线性增长（每 tick +0~1.2），与良品率负相关。当磨损超过预警阈值（65%）触发 L1 级别告警。

### 8.3 AI 运维 (AIOps)

**结构化诊断输出**: 要求 LLM 以 JSON 格式返回诊断结果（root_cause / recommended_action / confidence / need_isolation），确保可被程序化处理。置信度分数用于决定后续自动化程度——高置信度（>80%）建议可自动执行，否则升级人工。

**双重命令解析**: 自然语言控制采用关键词匹配 + LLM 语义理解的混合方案。关键词匹配处理常见操作（隔离、恢复、敌对、市场），LLM 兜底处理模糊指令。高风险操作（隔离节点、模拟敌对攻击）需要额外的确认码 `CONFIRM`。

**自动简报生成**: 每 20 个仿真周期，AI 根据当前工厂摘要（节点数、告警数、关键指标）生成一句话中文运行简报。不可用时回退到规则生成。

### 8.4 仿真与数字孪生

**因果约束仿真**: 不同于简单的随机数生成，仿真指标遵循物理因果关系：
- CPU 使用率 → API 延迟正相关 (latency = 15 + cpu * 0.35 + noise)
- 刀具磨损 → 良品率负相关（磨损越高，缺陷概率越大）
- 网络流量异常 → 触发 hostile-event 检测
- 隔离状态 → 所有指标大幅降低（CPU * 0.4, Net * 0.35）

**可复现性**: 仿真使用固定随机种子 (260507)，确保相同配置下每次运行结果完全一致，适合面试演示场景。

### 8.5 安全架构

**Token 双轨认证**: 前端/管理路径使用 `API_ACCESS_TOKEN`，节点数据上报路径使用 `NODE_INGEST_TOKEN`。实现了最小权限原则——即使前端 Token 泄漏，攻击者也无法伪造节点数据。

**速率限制**: 基于客户端 IP + 请求路径的速率限制，防止 DoS 攻击。每分钟 180 次限额。

**自然语言控制确权**: 高风险命令在 `plan_command()` 阶段自动标记 `requires_confirmation=True`，前端必须提供 `confirm="CONFIRM"` 参数才能执行。

### 8.6 前端架构决策

**无路由单页应用**: 故意不使用 Vue Router——四个视图通过 `activeView` 变量切换，减少依赖复杂度，适合演示场景。状态保持在组件实例中，不跨页面共享。

**无 UI 框架依赖**: 1679 行纯 CSS 实现完整工业控制台界面。不使用 Tailwind、Element Plus 等 UI 库——目的展示原生 CSS 能力并避免样式框架的"千篇一律"感。

**API 回退机制**: 所有数据获取均设计 fallback——API 可用时展示实时数据，不可用时回退到 `data.ts` 中的静态演示数据，确保离线演示能力。
