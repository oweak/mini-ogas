# Simulation And Production Boundary

Last verified: 2026-07-14.

## Current Classification

Mini-OGAS currently operates as a **single-host digital-twin laboratory** with `APP_ENV=digital_twin`, `DATA_SOURCE=simulated` and `CONTROL_MODE=operator_assisted`. It has no verified physical device connection and no physical write. SimPy is useful engineering machinery, but it is not an industrial connector, PLC, historian or proof of production behavior.

| Term | Required meaning |
|---|---|
| `simulated` | Generated by simple/SimPy runtime or another declared model |
| `fixture` | Deliberately injected test/demo scenario or response overlay |
| `replay` | Historical immutable records replayed without changing the original facts |
| `live` | Read from a governed real device/external system through an approved connector |
| `mixed` | Response contains more than one material source class |
| `fallback` | Authoritative source is unavailable and an explicitly marked fallback is returned |
| `unknown` / `未上报` | No accepted fact exists; no value may be invented |

Storing a simulated value in PostgreSQL or transporting it over NATS does not change it to `live`.

## What The Current SimPy Runtime Does

- Runs turning, milling and grinding profiles as local Python processes.
- Uses a random seed, scenario ID, run ID, simulation start and accelerated simulation clock.
- Models machine count, process time, nominal capacity, defects, WIP and selected fault conditions.
- Sends the strict current heartbeat payload to the Central API; the dashboard compatibility snapshot remains schema `2.2` while the NATS shadow envelope is schema `3.0`.
- Polls selected commands, validates versions/expiry/rate bounds and persists command idempotency/result state in local SQLite.
- Supports a part-flow mode and central part queue integration.

## What It Does Not Do

- It does not read a PLC, CNC controller, OPC UA server, Modbus register, MQTT industrial topic or historian.
- It is not calibrated against a named plant, machine model, material, cutting parameter set or maintenance record.
- It does not model mechanical/thermal physics sufficiently to authorize a physical setpoint.
- It does not prove network isolation, machine stop, maintenance dispatch or human completion.
- Its host CPU/memory values are process/host simulation context, not machine-controller telemetry.
- Its logical isolate operation does not open a contactor, stop a spindle or configure a switch/firewall.
- Its command effect verifier sees simulated heartbeat change, not independent physical readback.

## Current Data Boundary

| Data | Current class | Required UI/API behavior |
|---|---|---|
| SimPy output, WIP, rates, defects, wear | `simulated` | Display simulated source, run and scenario |
| Central random-walk simulation | `fixture`/legacy simulation | Exclude from canonical production path |
| Market simulator values | `simulated` / `demo-seed` | Never call external demand truth |
| Seeded machines, topology, inventory | `demo-seed` | Expose mixed provenance |
| Query mode bottleneck/starvation/emergency | `fixture` | Never return `live` |
| PostgreSQL replay | `replay` | Read-only and run-scoped |
| Missing KPI/due/completion | `unknown` | Display `未上报`; no browser formula |
| Future connector read | `live` only after approval | Include source, mapping version, quality and freshness |

## Time And Rate Boundary

The model stores both simulation time and wall-clock time. `simulation_speed` changes how quickly simulated time advances; it must not change the declared nominal physical capacity profile. `target_rate` currently means a simulated parts-per-minute constraint and is capped by the workshop profile. No target rate may be translated to a real controller tag until units, equipment capability, safe envelope and readback have been signed by the OT owner.

The current `clock_offset_ms` is calculated from central arrival skew. It is an observability hint, not evidence of synchronized clocks. Production requires NTP/PTP policy, drift monitoring and sequence-based ordering.

## Connector Maturity Stages

### Stage A: Offline Contract

- Recorded/vendor sample data only.
- Canonical mapping, units, quality and external ID reviewed.
- No network route to equipment.
- Exit evidence: contract tests and OT owner mapping approval.

### Stage B: Read-Only Lab

- Connector can authenticate to a lab endpoint with a read-only account.
- No write method/credential is present.
- Values are compared with the source and freshness/quality are visible.
- Exit evidence: disconnect/reconnect, duplicate/order, unit and stale-data tests.

### Stage C: Read-Only Pilot

- One named production asset/site, approved network conduit and per-connector identity.
- Mini-OGAS remains observational; no command reaches equipment.
- Reconciliation with operator/SCADA/historian over an agreed period.
- Exit evidence: signed pilot report, data-quality thresholds and incident rollback.

### Stage D: Shadow Command

- System generates a proposed command but never transmits it to equipment.
- Safety Governor and human approver compare the proposal with the actual operator action/result.
- Exit evidence: false-positive/negative review and safe-envelope evaluation.

### Stage E: Controlled Write

- Only a whitelisted low-risk command/tag is enabled.
- Per-device mTLS identity, scoped authorization, confirmation, interlock, rate limit, expiry and idempotency are mandatory.
- Independent readback verifies effect; missing receipt/readback is inconclusive, not retried blindly.
- Exit evidence: OT/security approval, rollback, emergency stop path and supervised drill.

### Stage F: Production Expansion

- Expansion occurs one capability/asset at a time after Stage E evidence.
- No AI autonomous physical write is implied or allowed by reaching this stage.

## Current Gate Position

Mini-OGAS is between Stage A and a simulated laboratory. It has not entered Stage B because there is no industrial connector or governed lab endpoint. `CONTROL_MODE` must remain read-only for any future physical connector until the required gates exist.

## Mandatory Claim Guard

Every status/report/demo must say:

1. source class;
2. run/scenario or external source ID;
3. freshness and quality when decision-relevant;
4. whether a command is proposal, approved, dispatched, applied or independently verified;
5. whether the effect is logical, simulated or physical.

Any screenshot or UI wording that hides these distinctions fails the truth gate even when the underlying code is technically functional.
